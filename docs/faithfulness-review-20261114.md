# W1 有限观察被扩大：输入审查、最小修正与复测

本说明更新于2026-11-14。案例均为虚构物业记录。原自然案例、原文、业务数据和旧核查结果继续保留。

## 结论与证据强度

本次已发现生成文字超出原文范围：W1的“厨房和卫生间的冷水龙头都不出水”被概括为“全屋无水”；W3只试了一个公共龙头，却在判断中被定性为局部异常。UTC时间与北京时间等值，但正文将观察时间称为反映时间，且直接显示UTC不利于理解。

已确认的是：

1. 用户展开的**这次已保存快照**保留W1完整description：“早上洗漱时，厨房和卫生间的冷水龙头都不出水了。家里的总阀没有动过，邻居家什么情况我还不知道，麻烦安排人来看一下。”观察2026-10-13 09:20北京时间；接收2026-11-13 21:45:54，与观察时间不同。
2. 代码路径：`routers/agent_runs.py` → `run_agent` → `read_automatic_agent_evidence` → `read_automatic_evidence`读取`ServiceRequestRead` → `original(row)`保留完整description，仅排除重放编号 → `GeminiEvidenceModel.suggest`把`evidence.model_dump_json()`交SDK → 保存同一evidence。
3. **修改前**已完成临时数据库到真实SDK序列化请求体的MockTransport截获。以W1–W4原文、日期和编号构造独立临时数据，经真正的网页API调用；W1/W2/W3的部位、冷水、检查范围、否定与未知均逐字保留，W4按另一栋排除，无计划和人工关联。发送JSON与API保存evidence逐项相同。
4. 修改后重复截获，原业务字段保持不变，只有程序派生时间标签增加。原UTC字段和description不改写。

**限制：**测试使用独立临时台账和模拟HTTP响应，不冒充用户Windows业务库或真实Gemini语义验收。旧运行没有保存网络请求或提示词版本；不能声称追回了那次真实网络包。结合已保存原文、当前调用代码和截获测试，有充分依据把本次范围扩大定位到生成表述，而不是当前取证层删掉“冷水”等内容。后续先导出真实旧运行，保留这一证据边界。

## 通用方法与本项目取舍

- [Google：Structured outputs](https://ai.google.dev/gemini-api/docs/structured-output) 区分格式约束和应用层值校验。当前Pydantic、引用存在和候选覆盖检查保留；不能因JSON有效就判语义正确。本轮不扩大输出schema或假装实现完整事实校验器。
- [Anthropic：Reduce hallucinations](https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations) 建议允许未知、用原文支撑陈述、核对引用，也讨论重复生成比较。本项目采用“先对照原文事实边界、保留未知、陈述对应具体出处”和少量同输入复测；这些是方法参考，不是对Gemini效果的保证。无需新增第二个审查Agent。
- [Min等，EMNLP 2023：FActScore](https://aclanthology.org/2023.emnlp-main.741/) 将生成内容拆为可逐条核对的事实。本项目借用细粒度验收思路，分别检查部位、冷热水、时间和因果；不安装其评估流水线，也不声称本项目已实现FActScore或具有其论文实验准确率。

“两个地方冷水异常”不能支持“全屋无水”，即使全屋无水在现实中可能成立。问题是缺少原文支持，不只是句子听起来不够保守。症状不同可支持安排分别检查，不能单独证明故障相互独立。原居民不知道邻居情况，和系统后来查到另一份居民报事可以同时成立，不能相互替代。

- 每次保存完整输入、摘要、新提示词、原始输出和结构校验结果；请求异常立即保存并停止余下调用，不自动重试。
