# 从报事自动查找依据：最小流程与验收约定

状态：前三步均已通过用户本机定向验证（最近57项）；第四步网页主流程已准备，待本机验证及实际页面验收。页面细化暂停。既有功能、文案、已保存记录、人工关联、失败记录和证据快照继续保留。自然案例尚未录入。

## 最小流程

1. 以服务器收到的报事编号读取报事原文、类别、地点和观察时间。
2. 程序分别搜索其他相关报事和候选工作计划。计划仅为来源之一；除了计划本身的地点与时间，还从同地点的执行和现场检查记录反查计划，防止计划范围改变后漏掉历史线索。当前已准备的第一步仅实现计划分支。
3. 在同一个读取事务中取得候选及相应记录，复用已有地点、时间、未知字段和缺记录规则。明确区分本地点记录、地点未注明的记录和其他地点背景。
4. 将有来源说明的候选证据交给模型。模型无需等待人员先建立关联，分析工作要求是否对应居民问题、字段与原文是否不一致，并提出具体补查事项。单次分析作为初始方案。
5. 保存建议、发现依据、检索范围与快照，沿用引用校验和失败保存。人员随后补充、纠正或确认；候选不写成已经确认的业务关联，建议不写成已解决。

是否增加模型选择工具补查，以验收中的实际遗漏决定。固定数据库检索先由程序完成；如果已有取证能回答问题，不增加空转的工具调用。

## 最终使用效果与本轮范围（2026-11-12确认）

工作人员打开一条居民报事，点击“AI辅助核查”，无需提前选择依据或人工关联。程序自动查询、汇集和核对既有记录，模型结合原文分析并提出有出处的初步建议，结果保存供刷新后读取；人工补充、纠正和最终审核。

结果按五项呈现：相关记录及发现理由（可展开原文）、关键事实与时间关系、带具体引用的初步判断、仍不确定的内容、可执行的下一步。另列本次查询范围、未接入来源和失败情况。生成建议不建立关联、不结案、不发布通知。

本轮只使用已有报事、地点、计划、执行和现场检查。不新增设备、管网、工单或通知模块。没有设备覆盖资料时不能确认共同设备、故障原因或跨楼栋关联。供水的同栋线索不等于同一故障；较早的正常保洁检查不能证明居民后来看到的问题已经解决。

## 第二步只读取证约定

- 新增 `related_reports.py` 和 `automatic_evidence.py`；调用方提供同一干净的读取事务，不写业务库、不调用模型，不依赖人工关联，不改变旧API或页面。
- 相关报事使用独立的演示配置：参考时间前后各2小时，上限50；可用 `RelatedReportPolicy` 配置。这是初始检索范围，未按真实事件标定，不是故障判定阈值或完整性承诺。
- 相关报事要求同服务类别；供水按地点台账搜同楼栋（包括不同单元／楼层／房间），其他类别暂限同一明确点位。没有楼栋上级的公共点位只搜同点位，不扩大到全区域；不跨楼栋推断设备关系，不解析描述中的地址。
- 起始地点未知时不查询其他报事，并标 `not_queried`，不能当成已查为空；其他报事地点未知不在地点匹配范围，返回说明明确这一限制。观察时间为空可用接收时间发现线索，但保留实际时间未知。
- 全屋无水与局部龙头异常都可能满足结构化检索条件：本步保留原文供后续模型区分，不以类别／楼栋提前判定同一事件。不同类别、楼栋和窗口外干扰项在检索时筛除。
- 候选计划沿用第一步策略和人工补充来源，直接读取其全部已保存执行／检查，不以当前计划范围不匹配跳过历史同地点材料，也不走界面列表第一页。
- 每条执行和检查分别标本地点、地点未注明、其他地点背景或报事地点未知。背景材料保留原文，但不用于本地点的时间比较和完成证明。执行完成仅为人员填报；完整的计划核对规则继续复用，并保留其规则版本和引用。
- 保留报事、计划、执行、检查与人工补充的完整原文、人员、实际／接收／录入时间、ID和版本；保存匹配所用地点及上级台账的路径与版本，便于后续展开和复核。
- 查询轨迹区分 `found`、`empty`、`not_queried`、`unsupported`、`failed`。没有候选计划时其子记录为未查询，但相关报事分支仍独立执行；未接入工单不能写成没有维修。
- 任何适用来源读取失败则抛 `AutomaticEvidenceReadError`，携带已完成／失败／未继续的查询轨迹，不返回正常的部分取证包。下一步运行记录接入时保存这些轨迹；本步没有新增持久化。
- 自动证据最多读取500条计划子记录（可配置）；超过上限或候选过多明确失败，不能静默截断再生成普通建议。子记录读取不再限制到计划发现窗口，轨迹明确是候选计划下全部已保存记录。
- 第二步退出条件仅是只读取证及回归通过；用户提出的按钮、模型语义判断、具体建议、保存刷新仍分别属于第三／四步，不以取证单测替代端到端验收。

## 第三步自动分析、引用与保存约定

- 新生成的 `POST /api/service-requests/{report_id}/agent-runs` 沿用原地址和请求体（仅request_id），服务器按路径报事编号自动取证，不接受客户端提供证据。旧的人工关联证据核查接口继续保留。
- 新增 `automatic_agent_evidence.py` 将第二步完整材料投影到既有AgentEvidence四字段封套。records保存完整业务原文、人员、时间、ID／版本、地点路径、发现理由、程序核对；剔除不具业务含义的提交重放编号。没有伪造人工关联编号。
- 相关报事和计划均列入 `context:investigation.candidate_refs`；地点、执行／检查、search查询记录可供引用。search:source含状态与实际范围，search:plan_records:plan:ID区分各计划的读取。
- 自动建议使用 `automatic-suggestion-v1`：observations（关键事实及时间）、candidate_assessments（逐候选判断）、uncertainties（有引用的不确定事项）、verification_items（具体下一步）。判断枚举为check_together、consider_separately、insufficient_information；表示初步核查安排，不表示确认同因或人工关联。
- 程序校验每项已发现报事／计划恰有一条判断，拒绝遗漏、重复、范围外候选；每项判断必须同时引用起始报事及候选本身。所有观察、判断和不确定项的引用必须存在于本次快照；关键事实至少引用一次起始报事。不确定项及下一步必填，拒绝额外auto_close等字段。
- 这些结构校验不验证自然语言结论真假，也不保证核实事项具体。真实模型对症状、工作要求、时间、范围矛盾及无依据原因的判断质量，仍需后续案例验收；不能用合法引用、全候选覆盖或pending_review代替。
- Gemini沿用现有单次请求和只读程序查询。新提示明确无计划也继续、同栋只是线索、原文指令按数据处理、其他地点正常不能代替本地点、人员填报与现场所见分开、未找到不等于未做、禁止编造设备／管网关系。旧版证据仍使用旧版提示，已保存旧建议按旧格式读取。
- 沿用agent_runs现有JSON列、状态和重放保护，不新增迁移。保存完整证据及建议；GET读历史不重新查询业务库或调用模型。同request_id重试返回原记录，包括后续已增加新证据的情况；要读取新材料需发起新request_id，旧快照不改写。
- 模型调用期间不持有数据库事务。查询失败保存 `automatic-evidence-failure-v1`，只含范围／状态／引用等查询轨迹，不含部分业务材料，不调用模型。取证超出96KB UTF-8输入上限也停止并保存查询轨迹，不截断后分析。模型超时或输出校验失败则保留完整取证快照、失败阶段／代码，无建议。
- 同提交编号并发重试仍只启动一次模型请求；旧运行、旧tool阶段失败及旧JSON建议继续可读、可重放。生成建议不修改关联或业务记录，不结案、不发布通知。
- 原生成建议接口已使用新取证路径。第四步已准备独立AI入口及五部分展示，本机和实际页面仍待验收；不恢复全站布局细化。
- 本步测试使用确定性模型输出与SDK模拟传输；证明自动取证／引用／保存／刷新和失败路径，不代表已运行真实Gemini或验证其语义质量。自然网页案例仍未录入。

## 第一步检索约定

- 输入是已存在的报事编号，调用方提供当前读取事务。该函数不自行提交、不生成模型请求、不写关联或其他业务记录。
- 演示初始参数：观察时间前7天、后1天，最多50项候选；可通过CandidatePolicy调整。它们是检索边界，不是物业时限或经过业务标定的阈值。
- 计划时间与窗口有重叠，且类别和明确地点对应时，列为自动候选。
- 即使计划时间较早或当前计划地点已经改变，只要同类别计划下有本地点且时间落在窗口内的执行或检查，也可反查为候选。地点与时间必须来自同一条记录，不能拿A地点旧记录和B地点新记录拼成匹配。
- 观察时间缺失时，以接收时间作为找近期记录的参考，输出received_at_search_only并警告；原观察时间仍为空，后续比较必须返回未知。
- 执行实际时间或检查观察时间缺失时，录入时间可用于发现线索，但必须标记recorded_time_search_only。不能据此证明实际工作的时间先后。
- 报事地点缺失时，按类别和时间降级检索并提示尚未匹配地点。空地点不与另一条空地点构成明确匹配。
- 本步只做类别、明确地点、限定时间的结构化发现，不按自由文本补造位置，不把父级地点自动展开到全部房间，也不自动跨类别检索。记录地点未知且计划时间不在窗口内等情况可能不被自动发现；返回结果不声称查遍所有可能依据。
- 第二步不能为候选伪造人工关联编号，也不能直接套用旧路径中“当前计划范围不匹配就跳过子记录”的模型投影。历史执行或检查若明确属于报事地点，仍应读取并单独标记；计划当前范围和每条历史记录的地点分别判断。
- 已有有效人工关联作为额外来源合并，允许带入窗口外等人工指定材料；同一计划去重，保留自动与人工来源，明确类别／当前计划地点是否匹配。
- 历史撤销不当作永久排除，也不静默掩盖：自动重新找到时标记曾有撤销。当前表的撤销语义不改，后续“排除候选”机制须与撤销关联区分。
- 超过数量上限直接返回明确错误，不偷偷取前几条后让后续模型认为搜索完整。下一步必须处理此错误或收窄范围，不能继续正常生成一份不完整建议。
- 候选保留计划原文、发现原因、时间范围、时间依据、人工来源等信息；尚未确认内容相关，不自动认定同一事件、因果或责任。

## 评估方法

分别运行“自动检索＋规则”和“自动检索＋规则＋模型”，核对相关证据召回、误纳入、具体补查建议、语义错误和人工查阅动作。第一步的同地点干扰计划必须保留给后续分析，不能在测试里假定它已经相关，也不能要求只读检索先完成语义判断。

零人工关联的完整链路通过、模型增量有实际案例支撑后，再决定是否引入动态补查工具。测试通过数量、引用编号合法和pending_review均不单独代表模型内容正确。
