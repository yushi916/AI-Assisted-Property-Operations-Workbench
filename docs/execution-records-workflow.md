## 一、先明确业务含义

案例：计划要求 A、B 两处大堂保洁，执行人只明确反馈 A 大堂已完成。

- 计划覆盖：PlanLocation 仍保留 A、B，不因一次执行反馈改变。
- 执行点位：ExecutionLocation 只登记明确反馈的 A。
- 完成状态：completed 表示执行人的声称，尚未经过独立巡查核实。
- 点位未知：location_ids=[]，表示具体点位待核实。
- 时间未知：两个 claimed 时间可为 null；recorded_at 单独记录何时录入。
- 收到未知或不完整的反馈仍需保留，后续由人员补查证据。

地点层级表示包含关系；计划和执行的关联表示明确选中的点位。
本版本按地点 ID 精确核对执行是否属于计划范围，不自动展开父地点或补全其他点位。
独立巡查、居民报事关联及履约判断随后实现。

## 二、从业务要求到文件和验证

| 步骤 | 实际文件 | 负责什么及验证方式 |
| --- | --- | --- |
| 输入与输出契约 | execution_schemas.py | 校验类型、非空文本、声称状态及带时区时间；拒绝客户端伪造服务端字段 |
| 数据映射 | models.py | ExecutionRecord 保存主记录，ExecutionLocation 保存明确点位；数据库约束提供底线保护 |
| 既有库演进 | migrations/versions/0004_execution_records.py | 在既有数据库增加两张表；迁移内容固定，历史版本不依赖后来变化的 ORM 定义 |
| 实际升级核对 | verify_execution_upgrade.py | 停服、备份后比较版本、旧结构和旧行，检查完整性与外键 |
| HTTP 与事务 | routers/executions.py | 校验计划和明确范围；主记录与点位一起提交或回滚；处理重复、冲突和查询 |
| 页面接线 | main.py、templates/executions.html、static/plan-list.js | 提供网页，从选定计划进入执行页面 |
| 录入交互 | static/executions.js | 读取计划点位、暂存原提交、保存回执、422 修正、冲突提示和原样重试 |
| 查询交互 | static/execution-list.js | 按计划查询、分页和详情；导入录入脚本；区分查询失败与空记录 |
| 自动回归 | tests/test_execution_*.py、tests/test_executions_api.py、tests/test_execution_form.cjs | 分别验证输入、结构、事务、接口、页面接线及表单交互 |
| 版本保存 | .github/workflows/tests.yml 与 Git 提交 | 检查文件齐全，在 Windows、Ubuntu 重跑 Python 与 JavaScript 回归 |

Schema、ORM 模型和迁移分别解决输入输出规则、代码如何操作数据、已有库结构如何变化。
仅增加表单交互时修改 HTML/JavaScript；新增表或字段时才安排结构迁移。
单个字段是否合法可在 Schema 校验；是否属于某项计划需要查询数据库，由接口校验。
测试先使用隔离数据库；通过后再按备份和核对流程升级实际数据库。

## 三、关键实现与对应测试

计划和执行分开保存，保留“计划要求什么”和“执行人明确声称做了什么”的差异。
API 测试 test_all_claims_can_keep_unknown_times_and_scope 验证四种完成声称
均可保留空点位、空时间；保存四条主记录，同时没有产生执行点位关系。

网页在 fetch 之前，用 sessionStorage 暂存 request_id 和 payload。
pending 状态的重试发送已保留的 payload；422 明确拒绝后允许修改，沿用提交编号。
测试 ambiguous save then reload retries original payload, one record
模拟后端已保存而回执丢失，验证刷新恢复后仍发送相同编号和内容。
测试中的 Map 是模拟后端；真实 SQLite 的事务与去重另由 API 测试和实际只读计数验证。

为检查回归是否能发现问题，AI 隔离验证曾分别临时改为：
未知点位自动填成全部计划点位、重试时从表单重建描述、422 修正后生成新提交编号。
对应回归均失败；这些临时错误没有交付为业务代码。
